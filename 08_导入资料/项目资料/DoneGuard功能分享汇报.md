# DoneGuard 功能分享汇报

## 一、为什么要做 DoneGuard

我们这段时间用 Codex 做了很多任务，包括股票筛选、飞书表格写入、多晶硅产业链研究、网页数据整理、在线表格批量更新等。整体感受是：AI 很适合做执行，但它有一个很典型的问题，叫“看起来完成了，但不一定真的完成了”。

这个问题不是简单把提示词写得更详细就能彻底解决的，因为主任务 AI 本身既在做事，又在判断自己有没有做对。它天然容易相信自己的执行结果，尤其是在任务链条比较长、涉及网页、表格、接口、数据口径时，出错点会被隐藏在中间步骤里。

所以 DoneGuard 要解决的不是“让 AI 更努力”，而是把验收流程制度化：

- 主任务 AI 负责执行。
- 测试方案 Agent 负责提前写验收标准。
- 人工先确认测试方案。
- 独立测试 Agent 按方案验收。
- 验收必须留下证据，而不是只说“已完成”。

一句话概括：以后不要只问 Codex“你做完了吗”，而是要问“你怎么证明你真的做完了”。

## 二、我们之前遇到的典型问题

### 1. 表面完成，但实际没有写对

典型场景是飞书在线表写入。页面看起来输入了内容，甚至前端看起来也保存了，但实际可能存在几个问题：

- 输入框需要失焦才保存，AI 点击或粘贴后不一定真的触发保存。
- 在线表格分页、筛选、排序后，行号可能和本地文件不一致。
- 只看前端显示，无法证明线上数据真的已经写入。
- 如果没有读回验证，就容易把“粘贴过”误认为“写成功”。

这类问题在在线表格、网页后台、数据库写入里都非常常见。

### 2. 数据口径看起来对，但实际拿错了

在股票筛选和财务数据任务里，我们遇到过类似问题：

- Q1 利润同比到底是 2026Q1 还是 2025Q1，列名不直观时容易误判。
- 网页上的 `netProfitMap.2026.q1Gr` 和本地计算口径需要校对，不能默认一致。
- PE TTM、静态 PE、一季度年化 PE 容易混用。
- 财报数据里归母净利润、扣非归母净利润、一次性收益也容易混在一起。

AI 很擅长整理表格，但如果没有明确验收口径，它可能会把“字段存在”当作“字段正确”。

### 3. 本地旧表和线上表不一致

这是 DoneGuard 测试里暴露出来的一个关键问题。

在飞书 `表2_下游需求` 备注写入任务中，第一次正式验收失败。原因不是备注内容写得不好，而是主任务使用了本地旧预期表，里面多了一行 `鑫华科技 / 科创板在审`，但线上表里这一行已经不存在。结果从第 5 行开始，备注整体串行。

如果只抽查前几行，这个问题可能发现不了；如果只让主任务 AI 自己检查，它也可能因为沿用了自己的本地映射而继续判断“没问题”。

最后的修复方式是：

- 不再按本地旧行号写入。
- 先读取线上真实股票列表。
- 用 `股票简称 + 股票代码` 做主键匹配。
- 再写入目标备注列。
- 写完后全量读回 `行号 + 股票简称 + 代码 + 备注`。

这个案例说明：在线表格任务不能信本地行号，必须以线上真实数据为准。

### 4. 主任务 AI 自己测试，容易漏掉自己犯的错

AI 自测有用，但不够。因为它的检查通常沿用同一套上下文、同一套假设、同一份中间文件。如果它前面就拿错了数据，后面自查也可能继续拿错。

所以 DoneGuard 强调“独立验收”。测试 Agent 不应该简单相信主任务 AI 的结论，而要基于批准后的测试方案，重新读取证据、重新比对结果。

### 5. 复杂网页不适合大批量直接点击

雪球、飞书、动态网页都有不稳定因素：

- 网页会拦截访问。
- 页面状态会变。
- 数据可能分页。
- 输入保存依赖前端事件。
- 大批量点击容易漏行、串行或保存失败。

所以 DoneGuard 形成了一个原则：能用接口或本地文件生成，就不要优先靠前端点击；必须通过前端操作时，也必须做读回验证。

## 三、DoneGuard 的核心设计

DoneGuard 不是一个聊天提示词，而是一套固定流程。

### 1. 三个角色

第一个是主任务 AI。它负责真正做事，比如生成备注、写入飞书、整理数据、改代码。

第二个是测试方案 Agent。它不直接执行任务，而是先看任务目标、上下文、历史风险，写出“这个任务做完后应该怎么验收”。这一步要让人过一遍，因为人可以补充业务判断，也可以删掉没必要的测试项。

第三个是测试执行 Agent。它拿到人工确认后的测试方案，独立执行检查，最后输出验收报告。

### 2. 人工确认点

DoneGuard 不是完全自动化黑盒。它在测试方案阶段保留人工确认：

- 如果测试方案合理，就直接确认。
- 如果测试方案太宽，可以删掉。
- 如果测试方案漏了重点，可以补充。
- 如果这个任务不需要验收，也可以放弃。

但一旦测试方案确认，测试执行 Agent 就不应该反复找人确认，除非涉及删除、写入、付费、泄密或越权。

### 3. 证据优先

DoneGuard 的验收不是靠一句“已完成”，而是靠证据。常见证据包括：

- 线上读回 JSON。
- 写入前后的 TSV / Excel。
- 行级比对报告。
- API 返回结果。
- 截图。
- 数据来源链接。
- 测试日志。
- 失败复现步骤。

尤其是表格和数据库任务，最重要的是“写完后读回来”。

### 4. 结构化沉淀

每个 DoneGuard 任务都会生成 `.doneguard` 工作区，里面存：

- `task.md`：任务说明。
- `test_plan.md`：测试方案草稿。
- `approved_test_plan.md`：人工确认后的测试方案。
- `verification_report.md`：最终验收报告。
- `evidence/`：证据文件。
- `artifacts/`：打包材料、面板、桥接请求等。

这样做的好处是：任务可以交接、复盘、回滚，也可以给另一个 AI 或同事继续接手。

## 四、实际案例复盘

### 案例一：飞书表2下游需求备注写入

任务目标：给飞书在线表 `表2_下游需求` 写入股票备注。

第一次结果：验收失败。

失败原因：

- 主任务使用了本地旧表。
- 线上真实表已经和本地表不一致。
- 本地预期表多了一行，导致第 5 行开始串行。
- 如果只看部分行，可能发现不了。

DoneGuard 发现的问题：

- 独立测试 Agent 全量读取线上 `C2:E30`。
- 按 `行号 + 股票简称 + 代码 + 备注` 逐行比对。
- 发现从第 5 行开始备注错位。

修复方式：

- 重新读取线上真实行。
- 按 `股票简称 + 股票代码` 生成备注映射。
- 通过飞书开放接口写入，不再依赖前端批量粘贴。
- 写入后全量读回验证。

最终结果：

- `E2:E29` 共 28 条有效股票备注全量匹配。
- `E30` 残留内容已清空。
- 二次验收通过。

这个案例的价值最大，因为它证明 DoneGuard 不是走流程，而是真的能抓出主任务没有发现的问题。

### 案例二：飞书表4上游硅基材料备注写入

任务目标：给 `表4_上游硅基材料` 写入备注。

这次采用了前面总结出来的正确流程：

- 先读取线上真实子表。
- 确认目标 `sheetId` 和标题。
- 读取线上股票简称、代码、原备注。
- 按 `代码 + 股票简称` 生成备注映射。
- 只写目标备注列。
- 写完后全量读回。
- 独立验收逐行比对。

最终结果：

- 线上有效行 10 行。
- 写入范围 `E2:E11`。
- 读回范围 `C2:E11`。
- 主线程机械读回通过。
- 独立验收通过。

这个案例说明：同样是飞书表写入，只要流程对了，就可以把风险降很多。

### 案例三：飞书表3设备辅材耗材备注补全

任务目标：补全 `表3_设备辅材耗材` 的备注内容。

执行方式：

- 读取线上 `表3_设备辅材耗材` 的真实行。
- 生成 24 行预期备注。
- 写入 `E2:E25`。
- 写入后读回 `A2:AZ25`。
- 用机械报告验证行数、范围、失败项。
- 再用 DeepSeek 做正式交叉验收。

最终结果：

- 预期行数 24 行。
- 实际读回 24 行。
- 失败数 0。
- DeepSeek 验收结论为通过。

这个案例证明 DoneGuard 已经可以用于正式任务，不只是概念验证。

## 五、DoneGuard 已经改进了哪些问题

### 1. 从“提示词约束”升级为“流程约束”

以前我们会在提示词里写“做完后自己检查一下”。但这还是让主任务 AI 自己判断自己。

现在 DoneGuard 把流程拆开：

- 主任务做事。
- 测试方案单独生成。
- 人工确认验收标准。
- 独立 Agent 验收。

这比单纯优化提示词更稳定，也更容易复用。

### 2. 从“抽查”升级为“全量验证”

尤其是表格写入任务，DoneGuard 默认要求：

- 行数核对。
- 主键核对。
- 写入范围核对。
- 全量读回。
- 失败项列出。

这能避免“前几行没问题，但后面串行”的情况。

### 3. 从“按行号写入”升级为“按主键匹配”

这是飞书表任务里最重要的改进。

旧方式是：本地第几行，对应线上第几行。

新方式是：先读线上真实行，再按 `股票简称 + 股票代码` 匹配。

这样即使线上删行、换行、排序变化，也不容易串行。

### 4. 从“网页点击优先”升级为“接口/文件优先”

现在的原则是：

- 优先本地生成 Excel / TSV / JSON。
- 优先用 API 写入和读回。
- 前端点击只作为不得已方案。
- 前端操作后必须读回验证。

这对飞书、雪球、网页表格这类任务很重要。

### 5. 从“任务结束即消失”升级为“证据沉淀”

DoneGuard 会保留：

- 测试方案。
- 人工确认版本。
- 写入证据。
- 读回证据。
- 验收报告。
- 失败原因。

这些材料后续可以复盘，也可以作为团队 SOP 的样例。

## 七、目前还存在的问题

### 1. 独立 Agent 还没有完全自动化

现在 DoneGuard 可以生成给 Codex Desktop / spawn_agent 的任务包，但自动打开独立 AI 窗口、自动投递任务、自动回收报告，还需要继续桥接。

当前更像是“半自动独立验收”：

- 任务包可以自动生成。
- 独立 Agent 可以按任务包验收。
- 但中间的调度还没有完全产品化。

### 2. Claude Code 还需要完成本机桥接

Claude Code 的命令行能力已经预留，但还要完成登录、命令封装、环境变量配置和稳定性测试，才能作为正式 provider。

### 3. 控制面板还比较基础

现在的看板能展示任务，但还不是一个完整产品。后续可以补：

- 新建任务按钮。
- 测试方案确认按钮。
- 验收进度状态。
- 失败项高亮。
- 证据文件入口。
- 多模型结果对比。
- 历史任务筛选。

### 4. 测试方案质量还需要长期调优

测试方案 Agent 有时会写得太泛，有时会漏掉业务关键点。比如投研任务里，不能只验证“表格有内容”，还要验证：

- 数据来源是否可靠。
- 财报口径是否正确。
- PE 类型是否混淆。
- 是否存在一次性收益扰动。
- 是否用错年份或季度。

所以 DoneGuard 不是一次性做完，而是要持续沉淀行业和任务类型的验收模板。

### 5. 研究类任务仍需要人做最终判断

像股票研究、多晶硅产业链、雪球评价综合判断这类任务，DoneGuard 可以验证：

- 有没有来源。
- 行数是否完整。
- 数据是否读回。
- 口径是否一致。
- 是否有明显缺项。

但它不能完全替代人的投资判断。比如“这家公司是否值得买”“弹性是否足够大”，最终仍然需要人结合策略目标判断。

### 6. 高风险写入任务仍要保留人工确认

DoneGuard 可以自动验收，但不能无脑自动写入。涉及这些动作时，仍然要人工确认：

- 删除数据。
- 覆盖线上表。
- 写数据库。
- 花钱调用。
- 使用敏感密钥。
- 大批量更新第三方网页。

## 八、后续改进方向

### 1. 自动打开独立 AI 窗口验收

目标是让 DoneGuard 能做到：

- 主任务完成后自动打包证据。
- 自动创建独立测试 Agent。
- 自动把测试方案和证据交给它。
- 自动回收验收报告。
- 自动更新看板状态。

这样就更接近刘大最初提到的“主任务 AI、测试方案 AI、测试执行 AI 三个窗口协作”。

### 2. 多模型路由

后续可以形成固定路由：

- 测试方案优先 DeepSeek。
- 代码类验收可用 Codex Desktop。
- 研究类和逻辑交叉检查可加 Claude Code。
- 高风险任务跑多模型交叉验证。

这样可以降低单一模型上下文污染和盲区。

### 3. 做成更强的 UI 面板

理想状态下，团队成员不需要记命令，只需要在面板里操作：

- 新建任务。
- 粘贴任务描述。
- 生成测试方案。
- 人工确认或修改。
- 上传证据。
- 启动验收。
- 查看失败项。
- 标记通过或返工。

命令行适合开发阶段，团队推广更适合面板化。

### 4. 建立团队验收模板库

不同任务要有不同模板：

- 飞书表格写入模板。
- Excel 数据处理模板。
- 股票财务数据核验模板。
- 网页自动化模板。
- 前端页面模板。
- 后端接口模板。
- 数据库写入模板。
- 投研报告来源核验模板。

模板越多，后续测试方案 Agent 写出来的东西就越贴近团队真实工作。

### 5. 和共享 MD / 项目交接系统结合

DoneGuard 可以和之前讨论的共享 MD 体系结合：

- MD 记录项目核心信息。
- DoneGuard 记录验收过程。
- Git 或压缩包记录实际文件。
- 看板记录任务状态。

这样项目转交给同事或另一个 AI 时，不只是给一个聊天记录，而是给一套“任务说明 + 当前文件 + 决策记录 + 验收证据”。

## 九、适合团队使用的标准流程

以后遇到复杂任务，可以按这个流程走：

1. 主任务开始前，先初始化 DoneGuard。
2. 让测试方案 Agent 根据任务生成验收清单。
3. 人工确认测试方案。
4. 主任务 AI 执行任务。
5. 主任务 AI 产出证据，不能只口头说完成。
6. 测试执行 Agent 按批准后的方案独立验收。
7. 如果失败，带着失败项返工。
8. 如果通过，把报告和证据沉淀到项目目录。

最适合强制使用 DoneGuard 的任务：

- 写入线上表。
- 修改数据库。
- 批量处理数据。
- 投研数据来源核验。
- 财务指标计算。
- 前后端联动功能。
- 任何失败成本高、返工成本高、容易“看起来完成”的任务。

## 十、分享时可以强调的核心观点

第一，DoneGuard 解决的不是 AI 不会做事，而是 AI 做完之后谁来证明它真的做对了。

第二，复杂任务不能只靠主任务 AI 自测，因为它会沿用自己的错误假设。

第三，验收标准要前置，不能等做完之后再临时想怎么检查。

第四，在线表格和数据库类任务必须读回验证，否则不算完成。

第五，DoneGuard 的核心价值不是多一个工具，而是把“验收”从人的临时经验变成团队可复用流程。

## 十一、100 字以内总结

DoneGuard 是一套防止 AI “假完成”的独立验收机制。它把主任务、测试方案和测试执行拆成不同角色，先由测试方案 Agent 写验收标准，人工确认后，再由独立测试 Agent 按证据验收。当前已在飞书表格写入任务中跑通，并成功发现过串行写入问题。后续重点是自动化独立 Agent、完善多模型路由和控制面板。
